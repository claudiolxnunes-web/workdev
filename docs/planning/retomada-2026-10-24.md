## Item 1 — medição: o que os números apontaram

O `timings` do llama-server (`prompt_ms` = prefill, `predicted_ms` = geração,
`cache_n` = o que veio do KV cache) agora é gravado por execução em
`tmp/bancada/<modelo>/_resumo.json`, no `registro.jsonl` e no evento SSE `fim`.
Agregação: `python3 scripts/bancada_local.py medicoes` e `GET /api/bancada/medicoes`
(panel "Medições: prefill × geração" na página Bancada Local).

Primeira medição real (modelo `moe`, CPU, prompt de 282 tokens):

| Rodada | Prefill | Geração | Cache |
|---|---|---|---|
| 1ª (modelo ainda não carregado) | 26,0 s (282 tok; **inclui a carga do modelo**) | 5,2 s (32 tok, 6,2 tok/s) | 0% |
| 2ª (mesmo prompt, modelo quente) | 0,2 s | 2,1 s (27 tok, 12,9 tok/s) | 99% |

**Correção (medido depois, com o modelo quente):** a vazão real de prefill é
~47–61 tok/s (6.973 tokens novos em 113 s = 61,5 tok/s; 516 tokens novos em
11 s = 47 tok/s). Ou seja: do bucket de 26,0 s da 1ª rodada, ~20 s foram a
**carga do modelo**, não prefill. Prefill puro ≈ **20 s por 1.000 tokens**;
os 22–30k do harness do CLI dariam **~7 a 10 minutos** de prefill.

O que isso muda no plano:

- **Contexto grande custa mais que resposta**: 22k tokens de prompt ≈ 7 min de
  prefill, contra ~80 s para gerar 1.000 tokens de patch (13 tok/s). A geração
  é mais lenta *por token*, mas o volume de contexto é o que mata.
- **O KV cache resolve o caso repetido**: o mesmo prompt na 2ª rodada reaproveitou
  99% do prefixo e o prefill caiu de 26 s para 0,2 s. O item 2 (`cache_prompt`) só
  vale para prompts *diferentes* com prefixo comum — que é exatamente o caso do
  harness do CLI (22–30k tokens de prompt fixo).
- A geração subiu de 6,2 para 12,9 tok/s entre as rodadas: a 1ª carregou o modelo.

Próximo passo: decidir o item 2 com esses números — medir quanto do prefixo do
harness é reaproveitado hoje antes de mexer em `cache_prompt`.

## Item 4 (broker na tela) — o prompt grande volta?

Pergunta: levar o broker para a tela não cai de volta no problema dos 22k tokens?

Resposta curta: **não pelo mesmo motivo** — os 22k eram um preâmbulo *fixo* do
harness (schema de ferramentas, AGENTS.md, histórico), repetido em toda requisição
e sem relação com a tarefa. O prompt da bancada é minúsculo: system do broker
109 tok, system do function calling 84 tok, schema das 3 tools 245 tok. São
~440 tok de "harness", não 22.000.

O risco real é outro — o histórico do broker **cresce a cada volta**. Medido:

| cenário | tokens novos | vindos do cache | prefill |
|---|---|---|---|
| 1ª chamada (38 tok) | 38 | 0 | 2,5 s |
| a mesma, de novo | 4 | 34 | 1,2 s |
| histórico **anexado** (+1.036 tok de uma leitura) | 1.070 | 34 | 28,7 s |
| mesmo histórico + sufixo pequeno | 21 | 1.100 | 1,1 s |

O prefixo que só cresce **é reaproveitado**: a última chamada re-prefillou só o
sufixo novo (21 tok). Então o multi-turno do broker **não é quadrático** — cada
volta paga só a leitura nova (~1.000 tok ≈ 20 s), não o histórico inteiro.

O perigo é a **evicção do cache**: o llama-server guarda um prefixo por slot.
Se outra requisição entrar no meio (outra tarefa, outro modelo), o histórico
todo volta a ser avaliado — 1.100 tok ≈ 28 s, 2.200 tok ≈ 46 s, e assim vai.

Três consequências de projeto para o item 4:

1. **Uma execução por vez por modelo.** A Bancada já é por clique, uma por vez.
   Paralelizar no mesmo modelo destrói o cache e o custo vira quadrático.
2. **Teto de contexto acumulado.** Nada impede o modelo de pedir 8 voltas ×
   3 leituras × 200 linhas ≈ 24k tokens — justamente o problema antigo. O
   broker precisa de um teto explícito de contexto, com o modelo avisado.
3. **Medir o caminho `broker`/`ferramentas`.** Ele **não grava medição hoje**
   (só o `rodar` grava). Sem instrumentar, o item 4 continua sendo palpite.
